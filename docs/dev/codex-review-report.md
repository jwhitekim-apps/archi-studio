# Archi Studio Codex 교차검증 보고서

검토일: 2026-10-18  
검토 기준: `docs/dev/codex-review.md`  
검토 대상: 당시 작업 트리의 미커밋 변경을 포함한 명세·문서·DB·서버·화면 셸·인증 구현

**높음 2건, 중간 8건, 낮음 2건**을 확인했다. 아래 위치의 줄 번호와 재현 결과는 검토 당시 상태를 기준으로 한다.

리뷰 과정에서 소스·문서는 수정하거나 커밋하지 않았다. 로컬 DB에는 검증용 데이터만 생성했고, 계정·로그인 시도 기록을 정리하거나 검증 트랜잭션을 롤백했다. 검증에 사용한 로컬 Supabase와 미리보기 서버는 종료했다. 운영 DB와 기존 서비스에는 접속하지 않았다. 이 보고서 파일은 리뷰 완료 후 사용자의 요청으로 작성했다.

타입 검사, 단위 테스트 **24개**, 인증 통합 테스트 **22개**, 빌드, 토큰 검사, OpenSpec 엄격 검증 **10개**는 모두 통과했다. 아래 문제 중 일부는 기존 테스트에 없는 추가 재현으로 발견했다.

## 검토 결과

### [심각도: 높음] 인코딩한 경로로 인증 가드를 우회할 수 있음 (영역 C·F)

- 위치: `src/lib/server/api-guard.ts:18`
- 근거: 가드는 인코딩된 `event.url.pathname`을 검사하지만, SvelteKit은 해당 경로를 디코딩해 실제 라우트에 연결한다.
- 재현: 쿠키 없이 `POST /%61pi/auth/logout` → 기대 401 → 실제 **204**. 라우트가 인증 가드를 거치지 않고 실행된다.
- 제안: 라우터와 일치하는 경로 표현으로 API 여부와 공개 경로를 판정하고, 인코딩 경로 회귀 테스트를 추가한다.

### [심각도: 높음] 미승인 계정이 직접 발급받은 Supabase 토큰으로 접근 가능 (영역 F)

- 위치: `src/lib/server/session.ts:33`
- 근거: 승인 검사는 앱의 로그인 함수에만 있다. 세션 검증은 Supabase 사용자라는 사실만 확인하며, 쿠키는 서명 없이 토큰 쌍을 인코딩한 값이다.
- 재현: 로컬 미승인 계정으로 Supabase 비밀번호 로그인 → 받은 토큰을 `archi_session`으로 인코딩 → `/api/auth/me` 요청 → 기대 접근 거부 → 실제 **200과 해당 사용자 정보**.
- 제안: 앱이 승인한 세션임을 서버에서 검증하거나, 보호 요청에서 승인 상태를 확인한다. 이는 기존 세션의 승인 취소 지연과는 별개의 우회다.

### [심각도: 중간] 허용된 길이의 번역문을 DB에 저장하지 못함 (영역 A·B)

- 위치: `supabase/migrations/20261018000400_history.sql:12`
- 근거: 스펙은 5,000자까지 허용하지만, `(user_id, source_text)` B-tree 인덱스에는 원문 전체가 들어간다. 데이터 모델도 이 위험을 이미 언급한다.
- 재현: 압축되기 어려운 **4,992자** 원문 삽입 → 기대 저장 성공 → 실제 `index row size 5024 exceeds ... maximum 2704`. 검증 트랜잭션은 롤백했다.
- 제안: 원문의 해시를 인덱싱하고, 캐시 조회 때 원문 일치도 함께 확인한다.

### [심각도: 중간] 병렬 로그인 요청이 실패 횟수 제한을 초과함 (영역 F)

- 위치: `src/lib/server/auth-service.ts:98`, `src/lib/server/login-attempts.ts:17`
- 근거: 제한 조회와 실패 기록이 분리되어 여러 요청이 같은 실패 횟수를 보고 통과한다.
- 재현: 같은 IP에서 잘못된 로그인 **8건 동시 요청** → 기대 제한 초과 요청 거부 → 실제 **8건 모두 401**, 429 없음. 순차 요청 테스트는 통과한다.
- 제안: IP별 시도 판정을 원자적으로 처리하고, 진행 중인 시도도 제한에 포함할지 정의한다.

### [심각도: 중간] API 필드 타입과 DB 모델이 일치하지 않음 (영역 A·B)

- 위치: `docs/api/openapi.yaml:694`, `docs/api/openapi.yaml:627`
- 근거: 번역 이력 `id`는 API에서 UUID지만 DB에서는 bigint다. 논문 `year`는 API에서 정수지만 DB에서는 text이며, API의 `title`은 문자열만 허용하지만 DB에서는 null이 가능하다.
- 재현: 코드 추론. DB의 이력 ID `1`, 연도 문자열 또는 제목 null을 응답으로 변환 → 기대 계약에 맞는 응답 → 현재 문서에는 일관된 변환 규칙이 없다.
- 제안: ID 계약을 통일하고, 연도·제목의 정규화와 null 처리 규칙을 명시한다.

### [심각도: 중간] 세션의 ‘최대 30일’이 보장되지 않음 (영역 F)

- 위치: `src/lib/server/api-guard.ts:37`, `src/lib/server/session-cookie.ts:55`
- 근거: 토큰을 갱신할 때마다 쿠키 유효기간을 다시 30일로 설정하며, 로컬 Supabase의 세션 `timebox`도 설정되어 있지 않다.
- 재현: 코드 추론. 사용자가 계속 이용해 주기적으로 갱신 → 문서의 “최대 30일” → 실제 구현은 만료 시점이 계속 연장된다.
- 제안: 절대 만료가 의도라면 서버에서 시작 시점을 기준으로 제한하고, 활동 기준 만료가 의도라면 문서를 수정한다.

### [심각도: 중간] 프레임워크가 먼저 거부한 API 요청은 공통 오류 형식을 따르지 않음 (영역 C)

- 위치: `src/hooks.server.ts:5`, `openspec/specs/api-foundation/spec.md:10`
- 근거: SvelteKit의 CSRF 검사는 사용자 훅보다 먼저 실행된다.
- 재현: 외부 `Origin`과 폼 Content-Type으로 `/api/auth/login` 요청 → 기대 `{error:{code,message}}` → 실제 **403 일반 텍스트** `Cross-site POST form submissions are forbidden`.
- 제안: CSRF 보호를 유지하면서 프레임워크의 조기 오류까지 다룰 응답 경계를 마련하거나, 오류 계약의 적용 범위를 명시한다.

### [심각도: 중간] 비활성 전용 저대비 색을 일반 안내문에 사용함 (영역 D)

- 위치: `src/lib/components/AppShell.svelte:159`
- 근거: `.empty`는 비활성 컨트롤이 아닌 안내문인데 `--color-text-faint`를 사용한다. 흰 패널과 대비가 **2.885:1**이다. 일반 작은 글자는 4.5:1이 필요하며, 비활성 컨트롤에 대한 예외를 안내문에 적용할 수 없다. [W3C 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- 재현: 라이트 테마 설정 패널의 안내문 → 기대 읽을 수 있는 대비 → 계산상 기준 미달.
- 제안: 안내문에는 보조 글자색을 사용하고 비활성 색의 사용처를 제한한다.

### [심각도: 중간] 모바일 패널의 포커스 이동·복귀 처리가 없음 (영역 D)

- 위치: `src/lib/components/AppShell.svelte:17`, `src/lib/components/AppShell.svelte:84`
- 근거: 열기와 닫기는 boolean만 바꾸며 포커스를 이동하거나 복구하지 않는다.
- 재현: 코드 추론. 겹침의 “닫기” 버튼을 키보드로 실행 → 기대 열기 버튼으로 포커스 복귀 → 포커스된 버튼 자체가 제거되며 복귀 처리가 없다.
- 제안: 열기 버튼을 기억하고 패널 진입·닫기 시 포커스를 관리한다. 모달로 취급한다면 배경의 키보드 접근도 제어한다.

### [심각도: 중간] `.env.test`가 비밀 환경 파일 차단에서 제외됨 (영역 E)

- 위치: `.gitignore:16`
- 근거: `!.env.test`가 `.env.*` 차단을 해제한다.
- 재현: `git check-ignore --no-index .env.test` → 기대 무시됨 → 실제 무시되지 않음. 현재 추적된 환경 파일은 `.env.example`뿐이다.
- 제안: `.env.test` 예외를 제거하고 값 없는 예시 파일만 허용한다.

### [심각도: 낮음] 새 환경의 Node·브라우저 준비 단계가 부족함 (영역 E)

- 위치: `docs/dev/setup.md:25`, `scripts/shell-screens.mjs:9`
- 근거: 설치된 Vite는 Node `^20.19.0 || >=22.12.0`을 요구한다. 개발 문서에는 Node 선택과 Playwright 브라우저·시스템 의존성 설치 절차가 없다.
- 재현: 화면 검증 스크립트 실행 → 기대 Chromium 시작 → 실제 `libatk-1.0.so.0` 누락으로 종료.
- 제안: 정확한 Node 요구 버전과 Playwright 설치·실행 절차를 문서에 추가한다.

### [심각도: 낮음] 명세의 인증 예외·오류 우선순위가 일관되지 않음 (영역 A·C)

- 위치: `openspec/specs/auth/spec.md:74`, `openspec/specs/api-foundation/spec.md:12`, `docs/api/openapi.yaml:384`
- 근거: auth 스펙의 공개 예외에는 health가 빠져 있다. 404·405 시나리오는 인증 전제를 생략하며, OpenAPI 번역 설명에는 다른 논문의 캐시 재사용 시 이력을 추가한다는 확정 결정이 빠져 있다.
- 재현: 쿠키 없이 `/api/nope` 요청 → 없는 경로 시나리오만 보면 404 → 실제 401. 존재 은닉을 위한 구현은 타당하지만 시나리오가 모호하다.
- 제안: 공개 예외와 인증 우선순위를 통일하고 번역 이력 추가 규칙을 OpenAPI에도 반영한다.

## 응답 필드와 저장 컬럼의 구분

단독 컬럼이 없는 응답이라고 해서 모두 누락은 아니다.

| 구분 | 필드와 저장 방식 |
|---|---|
| 계산·일시적 응답 | `connected`, `zoteroConnected`, `hasPdf`, `paperCount`, `translationCount`, `analysisCount`, `nextCursor`, 동기화의 `added/updated/removed` |
| 외부 저장소·관계에서 구성 | 사용자 `id/email`은 `auth.users`, `markdown/updatedAt`은 Zotero, `lastSyncedAt`은 동기화 key/value, `paperIds`는 연결 테이블 |
| 직접 응답하지 않는 저장 컬럼 | 승인·로그인 제한 기록, 소유자 FK, Zotero 자격 정보, 항목 버전·첨부 키, 캐시 내부 ID와 동기화 시각, 일부 생성·수정 시각 |

## 대비 재계산과 알려진 사항

다크 대비는 재계산 결과 본문 **13.920**, 포인트 **6.054**, 비활성 **4.690**으로 문서의 반올림 값과 일치한다. 알려진 `.env.example`의 JWT 변수 누락 등은 새 문제로 재보고하지 않았다.
