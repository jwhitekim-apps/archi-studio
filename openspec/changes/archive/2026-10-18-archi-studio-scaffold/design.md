# Design

## Context

- 저장소에는 문서와 OpenSpec 파일뿐이고 코드가 없다. 이 서버(집 서버)에는 Node 20(nvm)과 Docker 29가 있고, 폴리오 컨테이너가 3002 포트를 쓰고 있다. Supabase CLI는 설치돼 있지 않다.
- 입력 문서: `archi-studio-api-spec`의 `design.md`(결정 2~5)와 `docs/api/data-model.md`(테이블 11개, 적용 순서). 동기는 proposal.md 참조.
- 벨루 디자인 값은 `web/src/shared/styles/index.css`에 CSS 변수로 잘 정리돼 있고(라이트만, Tailwind 병행, 레거시 별칭 공존), 폴리오는 `web/src/app.css` 한 파일에 변수가 있고 다크 모드가 있다(모서리는 하드코딩, 간격 토큰 없음).

## Goals / Non-Goals

**Goals:**
- 이후 change가 라우트와 화면만 얹으면 되도록, 앱 틀과 서버 공통 규칙과 로컬 DB를 한 번에 맞춘다.
- 토큰과 셸을 먼저 세워 벨루와 폴리오의 화면을 옮길 때 값 비교를 다시 하지 않게 한다.

**Non-Goals:**
- Tailwind 도입. 토큰은 순수 CSS 변수로 둔다(아래 결정 4).
- 화면 내용, auth 엔드포인트 구현, 운영 DB 적용, 배포 파이프라인.
- 컴포넌트 라이브러리 전체. 셸에 필요한 최소 부품(메뉴, 패널 틀, 버튼, 입력)까지만 다룬다.

## Decisions

**1. SvelteKit(Svelte 5) + TypeScript strict, Node 어댑터.**
핸드오프에서 정한 스택이다. 이후 Docker와 Cloudflare Tunnel로 올리는 현재 배포 방식과 맞아서 서버리스 어댑터 대신 Node 어댑터를 쓴다. 패키지 매니저는 npm이다(벨루와 폴리오 모두 npm, 비서도 npm workspace). 대안으로 pnpm은 새 도구를 하나 더 늘려서 뺐다.

**2. Supabase CLI는 devDependency로, 로컬 DB는 `supabase/` 폴더에.**
전역 설치 없이 `npm run`으로만 쓴다. 마이그레이션은 `supabase/migrations/`에 타임스탬프 이름으로 두고, 파일 순서가 곧 `data-model.md` 7절의 생성 순서(`archi_profiles` → … → `archi_briefing_papers`)가 되게 쪼갠다. 한 파일에 몰지 않고 테이블 묶음별로 나누는 이유는 롤백과 검토가 쉬워서다. 대안으로 Docker Compose에 Postgres만 띄우는 방식은 Auth 서비스가 없어서 로그인 골격을 검증할 수 없어 버렸다.

**3. 세션은 서버 훅이 쿠키를 읽어 사용자를 `locals`에 넣는다.**
쿠키 이름은 `archi_session`으로 확정한다(`archi-studio-api-spec` design 결정 4가 구현 단계로 미룬 값). 훅은 `/api` 요청마다 쿠키로 사용자를 확인하고, 공개 경로 목록에 없는 경로는 기본적으로 401로 막는다. 목록 방식(허용 목록)으로 하는 이유는 새 경로를 만들 때 보호를 깜빡해도 안전한 쪽으로 실패하게 하려는 것이다. 이 change에서 공개 경로는 `GET /api/health` 하나다. auth 엔드포인트가 구현될 때 그 경로들을 목록에 추가한다.

**4. 디자인 토큰은 순수 CSS 변수 한 파일에 두고 Tailwind는 쓰지 않는다.**
벨루는 Tailwind와 CSS 변수가 섞여 있고 레거시 별칭이 공존해서 값의 출처가 둘로 갈린다. 폴리오는 Tailwind가 없다. 새 앱은 Svelte의 컴포넌트 스타일과 변수만으로 충분하고 도구가 하나 줄어든다. 토큰 이름과 구조(간격 `xs~2xl`, 모서리 `sm/md/lg/pill`, 글자 크기, 레이아웃 치수)는 벨루 쪽이 더 정리돼 있어 그대로 가져온다. 다크 모드는 폴리오에만 있으므로 폴리오의 방식(시스템 설정 따르기)을 가져오되 모든 토큰에 다크 값을 짝으로 정의한다.

**5. 토큰 값 채택 기준: 구조는 벨루, 다크 값 도입은 폴리오, 색은 한쪽으로 통일.**
임시 비교(근거는 두 CSS 파일):

| 항목 | 벨루 | 폴리오 | 초안 채택 |
|---|---|---|---|
| 바탕 | `#f6f7f4`(연회색 녹색기) | `#f3f0e9`(따뜻한 베이지) | 벨루 |
| 포인트 색 | `#12876a`(녹색) | `#315a8a`(파랑) | 벨루 녹색(확정) |
| 글꼴 | Roboto, Pretendard | Pretendard Variable, 명조(Maru Buri) | Pretendard Variable 기본, 명조는 논문 본문용 보조 |
| 간격 | 4/8/12/16/24/40 | 토큰 없음 | 벨루 |
| 모서리 | 8/10/12/pill | 하드코딩(8~24) | 벨루 |
| 레이아웃 | 헤더 56, 사이드바 240/72 | 없음 | 벨루 + 오른쪽 패널 폭 새로 정함 |
| 다크 | 없음(`dark` 규칙 0건) | 시스템 설정 따름 | 폴리오 방식, 값은 새로 정함 |

오른쪽 설정 패널 폭과 다크 팔레트는 어느 쪽에도 없어서 새로 정한다. 최종 대응 문서는 이 표를 확장해 `docs/design/token-map.md`에 둔다.

**6. 오류 형식은 하나의 헬퍼와 `handleError` 훅으로 강제한다.**
각 라우트가 오류 본문을 직접 만들지 못하게, 서버 공통 모듈에 `{ error: { code, message } }` 생성 함수 하나만 두고 훅의 오류 처리도 같은 함수를 쓴다. 처리하지 못한 예외는 `internal_error`와 일반 문장만 내보내고 원문은 서버 로그에만 남긴다. 대안으로 라우트마다 직접 JSON을 만드는 방식은 형식이 어긋나기 쉬워서 뺐다.

**7. 셸은 CSS 그리드 3열이고, 좁은 폭에서는 두 패널이 겹침(오버레이)으로 바뀐다.**
메뉴와 설정 패널의 열림 상태는 각각 하나의 값으로 관리하고, 사용자가 접은 상태는 이 change에서 저장하지 않는다(새로고침하면 기본값). 저장은 필요가 생기면 이후 change에서 한다.

## Risks / Trade-offs

- [로컬 Supabase가 이 서버의 메모리를 많이 쓸 수 있다] → 첫 작업에서 시작 후 메모리와 포트를 확인하고, 문제가 있으면 필요 없는 서비스(스튜디오 등)를 끄는 설정을 문서에 남긴다.
- [폴리오 컨테이너(3002)나 다른 서비스와 포트가 겹칠 수 있다] → 시작 전에 사용 중인 포트를 확인하는 단계를 첫 작업에 넣는다.
- [`archi_session` 쿠키 이름은 실제 Supabase Auth 세션 쿠키 방식과 맞춰야 한다] → 인증 구현 change에서 쿠키를 만드는 쪽이 이름을 이 spec에 맞추고, 맞지 않으면 spec을 고친다.
- [뼈대에서 정한 폴더 구조가 이후 change 때 다시 바뀔 수 있다] → 라우트 폴더는 `archi-studio-api-spec`의 `/api/{자원}` 구조를 그대로 따라 최소로 만든다.

## Migration Plan

1. 로컬에서만 동작하고 운영에는 아무것도 적용하지 않는다.
2. 롤백은 이 change로 만든 파일을 지우는 것으로 충분하다(기존 서비스에 영향이 없다).
3. 마이그레이션 파일을 운영(벨루) DB에 적용하는 단계는 별도 change에서 `data-model.md` 7절 순서대로 한다.
