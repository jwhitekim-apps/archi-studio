# Design

## Context

- 동기와 지적별 검증 결과는 proposal.md 참조. 이 change는 `archi-studio-auth`의 커밋하지 않은 구현 위에서 계획했고, 그 구현이 먼저 커밋돼 있어야 한다.
- 현재 구조: `src/hooks.server.ts`가 `createApiHandle`(`api-guard.ts`)을 쓴다. 가드는 `event.url.pathname`과 `GET /api/health`, `POST /api/auth/signup`, `POST /api/auth/login` 허용 목록으로 보호 여부를 정하고, `verifySession`(`session.ts`)이 `getUser`와 만료 시 한 번 갱신으로 사용자를 확인한다.
- SvelteKit 2.70.3은 라우트 매칭 전에 경로를 `decode_pathname`(`%25`로 나눠 `decodeURI`)으로 디코딩하고, CSRF 검사(폼 형식 본문 + 쓰기 메서드 + 다른 `Origin`)를 `handle`보다 먼저 실행해 일반 텍스트 403을 돌려준다.
- 마이그레이션은 아직 운영(벨루) DB에 적용하지 않았다. 개발 DB는 로컬 Docker라 `npm run db:reset`으로 다시 만들 수 있다.

## Goals / Non-Goals

**Goals:**
- 인증 경계가 인코딩이나 직접 발급 토큰으로 뚫리지 않게 한다.
- 오류 형식과 세션 기간 같은 계약이 구현과 문서에서 같은 말을 하게 한다.
- 지적마다 실패하는 회귀 테스트를 먼저 두고 고쳐서, 같은 문제가 다시 생기지 않게 한다.

**Non-Goals:**
- 승인 관리 화면, 기존 벨루 사용자 이관, 로그인 화면.
- `GET /api/auth/me`의 추가 조회 제거(알려진 사항, 그대로 둔다).
- Node 22와 SvelteKit 3으로의 전환.
- 운영 DB 적용. 이 change의 DB 작업은 로컬 Docker에서만 한다.

## Decisions

**1. 경로는 SvelteKit과 같은 방식으로 디코딩한 뒤 판정한다.**
가드에 `routePath(url)`를 두고 `url.pathname.split('%25').map(decodeURI).join('%25')`로 라우터와 같은 표현을 만든다. `/api` 여부와 공개 경로 허용 목록 비교는 이 값으로 한다. 디코딩이 실패하면(`URIError`) 원문이 `/api`로 시작하는 요청은 보호된 것으로 보고 401을 돌려주고, 그 밖의 경로는 프레임워크에 맡긴다(프레임워크도 같은 이유로 400을 돌려 라우트가 실행되지 않는다). `%2F` 같은 예약 문자는 `decodeURI`가 풀지 않으므로 라우터도 다른 경로로 보고 API 라우트와 연결하지 않는다.
대안으로 `/api`가 아닌 경로도 모두 막는 방식은 화면 경로까지 로그인이 필요해져서 버렸다. 라우터 안에서 라우트별로 검사하는 방식은 새 라우트마다 빼먹을 수 있어 버렸다.

**2. 승인 확인은 `verifySession` 안에서 매 요청 한다.**
`createSessionVerifier`가 `isApproved(userId)` 함수를 함께 받아 `getUser`(또는 갱신) 성공 뒤 `archi_profiles.approved`를 service role로 조회한다. 행이 없거나 `approved`가 아니면 `null`(401 `unauthenticated`)을 돌려준다. 이렇게 하면 직접 발급받은 토큰과 승인 취소(이미 발급된 세션)가 같은 곳에서 막힌다. 조회 오류는 인증 오류가 아니라 서버 오류이므로 예외로 올려 500이 된다(실패하면 닫힌다).
`login`의 승인 확인은 그대로 둔다. 세션을 만들기 전에 403 `pending_approval`을 알려 주는 용도다.
대안으로 쿠키에 서버 서명을 넣어 앱이 발급한 세션만 인정하는 방식은 키 관리가 늘고 승인 취소는 여전히 못 막아서 버렸다. 요청마다 조회가 한 번 늘지만 베타 규모에서는 부담이 없다.

**3. 로그인 시도 제한은 DB 함수 하나로 원자적으로 판정한다.**
`archi_reserve_login_attempt(ip, max, window)`를 마이그레이션에 만든다. IP 해시의 `pg_advisory_xact_lock`을 잡고 창 안의 행 수를 센 뒤, 한도 미만이면 행을 하나 넣고 그 id를 돌려주고 아니면 `null`을 돌려준다. 오래된 행(24시간)은 같은 함수 안에서 지운다. `login`은 자격 증명을 확인하기 전에 이 함수로 자리를 예약한다. 결과에 따라 실패면 예약 행을 그대로 두고(실패로 센다), 성공과 미승인 403, 예기치 못한 예외면 `archi_release_login_attempt(id)`로 지운다. 서버가 예약 뒤에 죽으면 행이 남아 실패로 세어진다(닫히는 쪽).
대안으로 프로세스 안 뮤텍스는 재시작·다중 인스턴스에서 깨져서 버렸고, 조회 뒤 기록하는 현재 방식은 병렬에 약해서 바꾼다. 부수 효과로 같은 IP의 정상 로그인이 실패 5건과 동시에 오면 429를 받을 수 있는데, 같은 IP에서 이미 5건이 몰리는 상황이라 받아들인다.

**4. CSRF는 프레임워크 검사를 끄고 같은 규칙을 훅에서 직접 적용한다.**
`svelte.config.js`에서 내장 검사를 끄고(`csrf.trustedOrigins: ['*']`, 또는 deprecated `checkOrigin: false`; 2.70.3에서 어느 쪽이 실제로 동작하는지는 구현 첫 단계에서 curl로 확인한다), `hooks.server.ts`의 `handle` 맨 앞에서 프레임워크와 같은 조건(쓰기 메서드 + 폼 형식 본문 + `Origin`이 서버 출처와 다름)이면 거부한다. `/api`는 `{error:{code:'forbidden_origin',...}}` JSON 403이고, 그 밖의 경로는 지금과 같은 일반 텍스트 403이다. 조건을 프레임워크와 똑같이 두는 이유는 보호 범위를 줄이거나 넓히지 않으려는 것이다.
대안으로 오류 계약의 적용 범위를 "프레임워크 거부는 제외"로 줄이는 방식은 클라이언트가 두 가지 형식을 처리해야 해서 버렸다. 자체 구현은 보안 코드를 직접 갖는 부담이 있어 열린 질문에 남긴다.

**5. 세션 기간은 "마지막 요청 후 30일"로 문서를 맞춘다.**
구현(갱신 때마다 쿠키를 30일로 다시 설정)은 그대로 두고 스펙 문구를 구현에 맞춘다. 승인 확인이 매 요청 들어가므로 세션이 길어도 승인 취소가 즉시 반영돼 위험이 작다. 절대 만료(발급 후 최대 30일)가 필요하면 Supabase Auth의 `timebox`를 설정하는 방법이 있고, 열린 질문에 남긴다.

**6. 번역 이력 마이그레이션은 기존 파일을 직접 고친다.**
`20261018000400_history.sql`에서 `archi_translations.id`를 `uuid default gen_random_uuid()`로 바꿔 API의 `TranslationRecord.id`(uuid)와 맞추고, `(user_id, source_text)` 인덱스를 `(user_id, md5(source_text))` 식 인덱스로 바꾼다. 캐시 조회는 해시로 후보를 좁힌 뒤 `source_text` 일치도 함께 확인한다. 운영 미적용이고 개발 DB는 `db:reset`으로 다시 만들면 되므로 새 마이그레이션 파일을 덧붙이지 않고 고친다(적용 순서 기록이 한 벌로 남는다). 로그인 시도 함수(결정 3)도 `20261018000600_functions.sql`에 이어 쓴다.

**7. API와 DB 타입 차이는 변환 규칙으로 문서화한다.**
`papers.year`(DB text)는 API에서 integer 또는 null이다. 규칙: 문자열에서 처음 나오는 네 자리 숫자를 정수로 쓰고 없으면 null. `papers.title`(DB null 허용)은 API에서 항상 문자열이며 null이면 빈 문자열이다. 이 규칙을 `openapi.yaml` 설명과 `data-model.md` 대응표에 적는다. 스펙은 필드 형식을 정하지 않으므로 스펙 델타는 만들지 않는다.

**8. 안내문 색은 보조 글자 토큰으로, 포커스는 직접 관리한다.**
`.empty`의 색을 `--color-text-faint`에서 보조 글자 토큰으로 바꾸고, `text-faint`가 비활성 컨트롤 밖에서 쓰이는지 검색해 남은 곳도 고친다. 모바일 패널은 연 버튼을 기억해 두고, 열릴 때 패널 안 첫 포커스 가능한 요소로 포커스를 옮기고, 닫히면(버튼, 스크림, Escape) 열었던 버튼으로 되돌린다. 패널이 열려 있는 동안 나머지 영역은 `inert`로 둬서 탭 순서와 보조 기술에서 뺀다. 검증은 `scripts/shell-screens.mjs`에 포커스 검사를 더해 실제 브라우저로 한다.

**9. 문서 참조는 한곳으로 모은다.**
`codex-review.md`의 작업 F가 사라진 `codex-review-auth.md`를 가리키므로, 그 내용(작업 1~3과 이미 알려진 사항)을 `codex-review.md` 안에 직접 적고 참조를 없앤다. `setup.md`에는 Node 요구 버전과 Playwright 준비 절차를 적는다.

## Risks / Trade-offs

- 인증 경로를 고치므로 기존 통합 테스트(22개)가 깨질 수 있다. 회귀 테스트를 먼저 쓰고 고쳐서, 깨지는 기존 테스트는 계약이 바뀐 것인지 구현 오류인지 구분해 갱신한다.
- 요청마다 조회가 한 번 늘어난다. 느려지면 짧은 메모리 캐시를 둘 수 있지만, 승인 취소 지연이 생기므로 지금은 넣지 않는다.
- CSRF 자체 구현이 프레임워크와 어긋나면 보호가 약해질 수 있다. 같은 입력 표(출처 같음/다름/없음 × 본문 형식 × 메서드)로 양쪽 동작을 비교하는 테스트를 둔다.
- 마이그레이션 파일을 직접 고치면 이미 `db:reset`을 돌린 다른 개발 DB와 어긋난다. 이 저장소는 로컬 개발 DB가 이 서버 한 곳뿐이라 `db:reset`으로 맞춘다.
- Playwright 검증은 이 서버에 시스템 라이브러리가 없어 지난번에 임시 폴더의 라이브러리와 `LD_LIBRARY_PATH`로 우회했다. 그 임시 폴더가 사라졌을 수 있어 `setup.md`에 재현 절차를 먼저 적는다.

## Open Questions

1. **세션 기간 의미**: "마지막 요청 후 30일"(활동 기준, 지금 구현과 같음)로 문서를 정정할지, 발급 후 최대 30일(절대 만료)로 구현을 바꿀지. 추천은 활동 기준이다. 승인 확인이 들어와서 장기 세션의 위험이 작고 구현 변경이 없다.
2. **CSRF 자체 구현**: 프레임워크 검사를 끄고 훅에서 같은 규칙을 직접 적용할지, 오류 계약의 범위를 "프레임워크가 먼저 거부한 요청은 제외"로 줄일지. 추천은 자체 구현이다. 클라이언트가 형식 하나만 처리하면 되고, 같은 규칙을 테스트로 고정한다.
3. **마이그레이션 직접 수정**: 운영 미적용이므로 기존 마이그레이션 파일을 고쳐도 되는지. 추천은 고치는 것이다. 단 이 저장소 밖(다른 개발 PC 등)에 이미 적용된 로컬 DB가 있다면 알려 주어야 한다.
4. **미승인 토큰의 응답 코드**: 보호된 요청에서 미승인 계정에 401 `unauthenticated`를 줄지 403 `pending_approval`을 줄지. 추천은 401이다. 직접 토큰을 만든 쪽에 승인 상태를 알려 주지 않고, 쿠키를 거부하는 한 가지 경로로 통일된다.
