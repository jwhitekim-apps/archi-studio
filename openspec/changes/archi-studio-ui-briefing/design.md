# Design

## Context

- 계약: 메인 스펙 `briefing`(목록 `GET /api/briefings`, 상세 `GET /api/briefings/{id}`, 읽기 전용)와 `docs/api/openapi.yaml`의 `BriefingListItem`(`id`, `date`, `summary`), `BriefingDetail`(여기에 `body`, `paperIds`가 더해짐). 상세는 논문 `id`만 돌려주고 제목은 주지 않는다. 이 change는 이 계약을 바꾸지 않고 화면만 만든다.
- 앱의 현재 상태(직접 확인): 화면은 `src/routes/+page.svelte` 하나뿐이고, `AppShell.svelte`의 왼쪽 메뉴는 `['서재', '번역', '분석', '메모', '브리핑']` 글자 목록으로 링크가 없다. 공통 부품(카드, 빈 상태, 버튼 등)은 아직 없고 `archi-studio-ui-auth-library`가 만든다. 셸은 `hasPanel` 속성으로 오른쪽 패널을 접을 수 있다.
- 데이터가 만들어지는 곳: 비서(morning-desk)가 하루 한 번 브리핑을 만든다. 비서 코드는 카톡 말풍선(200자 안팎, 최대 8개)을 구역(먼저 할 일, 오늘 마감, 임박, 밀린 일, 메일·GitHub·폴리오 소스별, 서버 상태, 참고)으로 나눠 만든다. DB에 저장되는 `summary`와 `body`의 정확한 형식은 `briefing-store` change가 정하고, 브리핑 스펙도 "세부 형식은 구현 전에 보완한다"고 적고 있다. 그래서 이 화면은 본문의 구역 구조에 기대지 않는다.
- 데이터 모델: `archi_briefings(id, user_id, date, summary, body, created_at)`, 하루 한 번(`unique (user_id, date)`). `archi_briefing_papers`가 언급된 논문을 잇는다. 논문이 삭제되면 그 연결 행도 함께 지워진다.
- 보안 배경: 브리핑 본문에는 메일 제목, GitHub 제목처럼 바깥 사람이 쓴 글이 들어갈 수 있다(비서는 제목까지만 내보낸다). 화면은 이를 신뢰하지 않는 입력으로 다룬다.

## Goals / Non-Goals

**Goals:**
- 카톡 링크 한 번으로 오늘 브리핑을 읽을 수 있게 한다(로그아웃 상태여도 로그인 뒤 같은 곳으로 돌아온다).
- 본문에 어떤 글이 들어 있어도 화면 구조와 보안이 깨지지 않게 한다.
- 구현이 작아서 다른 화면 change의 공통 부품이 제대로 쓸 만한지 확인하는 첫 사용처가 되게 한다.

**Non-Goals:**
- 브리핑 생성·저장·수정·삭제, 검색, 필터, 읽음 표시, 알림.
- 본문의 마크다운 꾸밈(열린 질문 1).
- 논문 허브 화면 자체(`archi-studio-ui-paper-hub`).

## Decisions

**1. 주소는 `/log`(목록)와 `/log/[id]`(상세)이고, 상세 주소의 `id`는 브리핑의 UUID다.**
카톡 알림 링크가 이 주소를 쓴다(`briefing-store`가 만든다). API 경로도 `id`를 쓰므로 화면과 API가 같은 식별자를 가진다. 대안은 `/log/2026-10-18`처럼 날짜를 주소에 쓰는 것인데, 하루 한 번이라는 제약이 깨지면(예: 같은 날 재실행) 주소가 모호해진다.

**2. 첫 화면 데이터는 서버에서 불러오고, "더 보기"만 브라우저에서 불러온다.**
`+page.server.ts`의 `load`가 `event.fetch('/api/briefings')`로 같은 앱의 API를 내부 호출한다(쿠키가 같이 전달되고 인증 훅을 그대로 거친다). 덕분에 첫 화면에 내용이 바로 있고 401이면 서버에서 로그인으로 보낼 수 있다. "더 보기"는 브라우저가 `/api/briefings?cursor=...`를 부르고 받은 항목을 이미 보이는 목록 뒤에 붙인다. 이미 있는 `id`는 건너뛴다(중복 방지). 대안은 전부 브라우저에서 불러오는 것인데, 첫 화면이 비어 깜박이고 로그인 이동 처리가 화면마다 흩어진다.

**3. 본문은 이스케이프된 글자로만 그리고, 날짜는 문자열 그대로 가공한다.**
Svelte의 기본 `{값}` 표시(자동 이스케이프)만 쓰고 `{@html}`은 이 화면에서 쓰지 않는다. 줄바꿈과 긴 줄은 CSS(`white-space: pre-wrap`, `overflow-wrap: anywhere`)로 처리한다. 대안은 마크다운 렌더러(예: `marked`)에 정화(sanitize) 라이브러리를 붙이는 것인데, 저장 형식이 정해지지 않았고 의존성이 늘어나서 미룬다. `date`는 시간대 없는 날짜(`YYYY-MM-DD`)라서 `new Date()`로 바꾸면 시간대에 따라 하루가 밀릴 수 있다. 문자열의 연·월·일 부분으로 `2026년 10월 18일` 형식을 만들고 요일은 `Intl.DateTimeFormat`에 `timeZone: 'UTC'`를 지정해 구한다.

**4. 언급된 논문의 제목은 상세 화면이 논문 API로 하나씩 가져온다.**
상세 응답에는 `paperIds`만 있고 제목이 없다. 화면은 각 `id`에 `GET /api/papers/{id}`를 병렬로 부르고 `title`만 쓴다. 한 브리핑에서 처리할 논문은 최대 20편이고 넘으면 "외 N편"으로 줄인다. 제목을 못 가져온 논문은 "제목을 불러오지 못한 논문"으로 링크를 유지하고, 응답이 404인 논문(그 사이 삭제됨)은 목록에서 뺀다. 제목이 빈 문자열이면 "제목 없는 논문"으로 보인다(`papers` 제목 정규화 규칙). 대안은 브리핑 API에 제목까지 담게 하는 것인데, 이미 확정된 계약을 바꾸게 된다.

**5. 로그인이 필요하면 `/login?next=<원래 주소>`로 보낸다.**
`load`에서 401을 받으면 원래 열던 경로를 `next`로 붙여 로그인으로 `redirect`한다. 브라우저의 "더 보기"가 401을 받으면 이미 보이는 항목을 남기고 안내와 로그인 링크만 띄운다. `next`는 같은 사이트의 `/`로 시작하는 상대 경로만 허용해야 한다(바깥 주소로 보내는 공격 방지). 이 검사는 로그인 화면 쪽 책임이므로 `archi-studio-ui-auth-library`와 맞춰야 한다(열린 질문 2).

**6. 논문 링크는 `/papers/{id}`로 걸고, 도착 화면이 있는지는 이 change가 보증하지 않는다.**
도착지는 `archi-studio-ui-paper-hub`가 만든다. 이 change를 먼저 구현하면 링크를 눌렀을 때 "찾을 수 없음"이 나올 수 있다. 그래서 시험은 링크의 `href`가 `/papers/{id}`인지만 확인한다. 구현 순서는 `ui-paper-hub` 뒤를 권한다.

**7. 셸 연동은 최소로 한다.**
`/log` 계열 화면은 `hasPanel={false}`로 오른쪽 패널을 접고, 메뉴 "브리핑"에 `aria-current="page"`를 준다. 메뉴 전체를 링크로 바꾸는 일은 `archi-studio-ui-auth-library`가 먼저 하므로 여기서는 "브리핑"이 `/log`를 가리키는지 확인만 한다.

**8. 시험은 로컬 DB에 시험용 브리핑을 넣어서 한다.**
`scripts/seed-briefings.mjs`가 로컬 DB(`npm run db:start`)의 승인된 시험 계정에 브리핑을 넣는다. 데이터는 목록 페이지 나눔을 확인할 수 있게 `limit` 기본값(30)을 넘는 35건, 본문에 `<script>` 글자와 공백 없는 긴 주소가 있는 건, 논문을 언급한 건(시험용 `papers` 행 2개 연결)과 언급하지 않은 건이다. 화면 확인은 `scripts/briefing-screens.mjs`(Playwright, 기존 `scripts/shell-screens.mjs`와 같은 방식)가 맡는다. 운영 DB에는 어떤 것도 넣지 않는다.

## Risks / Trade-offs

- [서버의 내부 호출로 토큰이 갱신되면 새 쿠키가 브라우저까지 전달되는지 확실하지 않다] → 구현 첫 단계에서 만료된 접근 토큰으로 `/log`를 열어 `Set-Cookie`가 브라우저에 도착하는지 시험한다. 안 되면 결정 2의 대안(브라우저 불러오기)으로 바꾼다.
- [비서의 저장 형식이 정해지기 전에 만들면 본문 모양이 기대와 다를 수 있다] → 글자 그대로 보여 주는 쪽이 어떤 형식에도 안전하다. 형식이 정해지면 다음 change에서 꾸밈을 더한다.
- [논문 링크가 많은 브리핑은 제목 요청이 늘어난다] → 상한 20편과 병렬 호출로 제한한다.
- [`next` 파라미터를 잘못 처리하면 외부 주소로 보내는 구멍이 된다] → 로그인 화면 change와 같은 규칙(상대 경로만)을 쓰고, 이 화면의 시험에서 `next=https://example.com`을 보내 무시되는지 확인한다.
- [카톡 알림 링크의 주소 형식이 바뀌면 이미 보낸 링크가 깨진다] → 결정 1로 `/log/{id}`를 고정 계약으로 둔다.

## Migration Plan

1. 이 change는 새 화면만 추가하고 기존 기능을 바꾸지 않는다. 마이그레이션이 없다.
2. 운영 DB에는 접속하지 않는다. 시험 데이터는 로컬 DB에만 넣는다.
3. 롤백은 `src/routes/log/`와 시험 스크립트를 지우고 메뉴 항목을 원래대로 되돌리는 것으로 충분하다.

## Open Questions

1. **본문을 마크다운으로 꾸밀까요?** 추천은 처음에는 글자 그대로 보여 주고, `briefing-store`가 저장 형식을 정한 뒤 필요하면 정화 라이브러리와 함께 추가하는 것이다.
2. **로그인 화면의 주소와 돌아올 주소의 파라미터 이름**은 `archi-studio-ui-auth-library`가 정한다. 추천은 `/login?next=`이고, 그쪽 제안서와 맞춘다.
3. **상세 주소를 `id` 대신 날짜로 할까요?** 추천은 `id`를 유지하는 것이다(결정 1).
4. **한 브리핑에서 보여 줄 논문 링크 상한**은 20편이 적절한가? 추천은 20편이다.
5. **읽음 표시나 "오늘 브리핑 바로가기"** 가 필요한가? 추천은 데모 이후에 판단한다.
