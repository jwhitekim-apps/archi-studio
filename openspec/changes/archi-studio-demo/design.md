# Design

## Context

- 발표는 11월 24일 소프트컴퓨팅 세미나이고, 인터넷은 쓸 수 있다. 학교 로컬 LLM(학교 서버의 자체 서명 인증서로 접속하는 AI)은 앱을 돌리는 집 서버가 호출하므로 발표 노트북에는 인증서가 필요 없다. 이 서버에서 실제로 호출이 성공한다는 것은 비서의 기존 기록으로 알고 있고, 새 앱에서의 호출은 이 change 시점에 다시 확인해야 한다.
- 발표 노트북은 앱에 공개 주소로 접속한다. 공개 주소와 배포 위치는 아직 정해지지 않았다(`TODO.md` 5절 6번, `archi-studio-deploy-cutover`가 정한다).
- 분석 기능은 11월 10일까지 끝나지 않으면 기존 벨루의 분석 결과를 연결하는 예비안으로 간다(핸드오프 확정 결정 6번). 이 경우 데모에서 어느 결과가 새 앱의 것이고 어느 것이 기존 벨루의 것인지 정직하게 말해야 한다.
- 이 change의 산출물은 `docs/demo/` 아래 문서다. 코드는 바꾸지 않는다. 시험용 데이터를 넣는 스크립트가 필요하면 `scripts/demo-seed.*`로 만들되, 그 구현 여부는 시험용 데이터 방식 결정(아래 결정 3)에 따른다.

## Goals / Non-Goals

**Goals:**
- 발표자가 처음 보는 사람이어도 대본과 점검표만 보고 데모를 끝까지 진행할 수 있다.
- 장면마다 "통합했다"는 주장의 증거가 화면에 보인다.
- 인터넷이나 학교 LLM이 막혀도 발표를 이어갈 대체 경로가 있다.

**Non-Goals:**
- 새 기능 구현, 발표 슬라이드 디자인, 시연 중 실시간 코딩.
- 구 서비스(벨루, 폴리오) 종료. 그 시점은 `archi-studio-deploy-cutover`의 열린 질문이다.

## Decisions

**1. 데모는 3장면, 총 흐름은 "흩어짐 → 한 흐름 → 근거" 순서로 한다.**
- 장면 1(흩어진 모습): 기존 벨루, 폴리오, 비서의 화면 또는 정리된 표(프로젝트 3개, 로그인 3개, 언어 3개)로 시작해 문제를 보여 준다. 기존 서비스의 화면을 열려면 그 서비스가 켜져 있어야 하므로, 켜 둘지 캡처로 대신할지는 열린 질문에 둔다.
- 장면 2(통합된 한 흐름): 로그인 한 번 → 서재에서 논문 선택 → 논문 허브 → 분석 → 번역 → 메모 → 브리핑.
- 장면 3(통합의 근거): 같은 계정, 같은 논문 데이터, 같은 디자인, 하나의 AI 사용 원칙을 증거 표(결정 2)로 보여 준다.
- 대안으로 흐름만 보여 주고 근거 장면을 빼는 방법이 있었지만, 핸드오프가 "통합이 사실이 되려면 로그인, 메뉴, 논문 데이터가 정말 하나여야 한다"고 적었으므로 근거 장면을 유지한다.

**2. "통합했다"는 말마다 증거를 표로 둔다.**
`docs/demo/evidence-checklist.md`에 `주장 / 화면에서 확인하는 방법 / 확인 결과(통과, 실패, 예비안)`을 적는다. 예: "로그인이 하나다" → 한 번 로그인한 뒤 서재, 번역, 분석, 브리핑이 다시 로그인을 요구하지 않는다. "논문 데이터가 하나다" → 서재에서 연 논문의 제목이 분석, 번역 이력, 메모, 브리핑에서 같은 논문으로 보인다. "디자인이 하나다" → 모든 화면이 같은 토큰(색, 글자, 간격)과 3단 셸을 쓴다. 확인 결과가 실패이거나 예비안인 항목은 대본에서 그대로 말하거나 빼고, 말하지 못하는 주장은 발표에서 쓰지 않는다.

**3. 시험용 데이터는 데모 전용 Zotero 계정과 SQL 시드 둘 다 준비한다.**
- 기본: 데모 전용 Zotero 계정에 공개 논문 3~5편을 넣고 앱에서 연결·동기화한다. 이 방식이 앱의 실제 동기화 경로를 보여 준다.
- 예비: Zotero 연결이 안 될 때를 위해 같은 논문을 `papers` 테이블에 직접 넣는 SQL 시드를 준비한다(로컬 DB에서 먼저 검증, 운영 DB에는 백업 후 적용).
- 번역 이력, 분석 결과, 브리핑도 미리 한 번씩 실행해 두어 데모 중 AI 호출 지연이 길어져도 이전 결과를 보여 줄 수 있게 한다.
- 대안으로 SQL 시드만 쓰는 방법은 간단하지만 "정말 동기화된다"는 근거가 없어서 기본으로 삼지 않는다.

**4. 예비 영상은 전체 흐름을 한 번에 촬영하고 장면별로 나눠 둔다.**
- 데모를 실제 환경에서 처음부터 끝까지 한 번 녹화하고(화면 녹화와 마이크), 장면별로 잘라 둔다. 인터넷이 막히면 영상을, 학교 LLM만 막히면 이미 만든 결과 화면으로 대체한다.
- 영상은 발표 노트북 로컬 디스크와 USB 두 곳에 두고, 발표 전날 재생 점검을 한다. 모든 흐름을 녹화하려면 기능 동결 이후여야 한다.

**5. 발표 장소 점검은 노트북에서 앱을 열어 보는 순서로 한다.**
공개 주소 접속, 가입·로그인, 서재 로딩, 번역 스트리밍(글자가 흘러나오는지), 분석, 브리핑 목록의 순서로 확인한다. 학교 LLM은 집 서버가 호출하므로 노트북 쪽 인증서 문제는 점검에서 제외하고, 대신 집 서버의 상태(앱, 로컬 Supabase가 아니라 운영 DB 접속, 학교 LLM 응답)를 발표 전날과 직전에 한 번씩 확인한다.

**6. 리허설은 기능 동결 후 두 번 한다.**
첫 리허설은 대본대로 끝까지, 두 번째 리허설은 일부러 실패를 일으켜(인터넷 끊기, 학교 LLM 차단) 대체 경로를 연습한다. 결과는 `rehearsal-checklist.md`에 날짜와 함께 남긴다.

## Risks / Trade-offs

- [기능이 일부 미완성일 수 있다] → 증거 표(결정 2)의 실패·예비안 칸을 그대로 쓰고, 대본에서 그 장면을 빼거나 예비안(예: 분석은 기존 벨루 결과 연결)을 쓴다고 밝힌다. 거짓 주장보다 작은 데모가 낫다.
- [발표 환경의 네트워크가 막힌다] → 예비 영상(결정 4), 발표 전 현장 접속 시험.
- [AI 응답이 느리거나 실패한다] → 미리 만들어 둔 결과(결정 3)와 영상.
- [시험용 계정과 데이터가 운영 DB에 남는다] → 데모 전용 이름을 쓰고, 발표 후 정리 절차를 `seed-data.md`에 함께 적는다.
- [리허설 시간이 부족하다] → 기능 동결일을 발표 3일 전으로 잡고, 동결 이후에는 버그 수정만 한다(열린 질문에서 확정).

## Migration Plan

배포나 마이그레이션은 없다. 이 change의 문서는 `docs/demo/`에 추가만 하며 되돌릴 때는 폴더를 지우면 된다. 시험용 데이터를 운영 DB에 넣는 경우에는 `archi-studio-deploy-cutover`의 백업 절차를 먼저 따른다.

## Open Questions

1. **장면 1에서 기존 서비스 화면을 직접 열지, 캡처로 대신할지.** 추천은 캡처로 대신하는 것이다. 현장에서 기존 서비스 3개를 모두 켜 두면 점검 대상이 늘고, 발표 중에 로그인 3번이 필요해 흐름이 끊긴다. 정확한 문장은 "로그인이 3개였다"를 화면 캡처 3장으로 보여 주는 것이다.
2. **기능 동결일.** 추천은 발표 3일 전(11/21)이다. 그 뒤에는 버그 수정과 리허설만 한다.
3. **발표 환경 선택.** 추천은 공개 주소로 접속하는 방식이다(노트북에 설치할 것이 없다). 인터넷이 막힐 때를 위해 예비 영상을 같이 두고, 노트북에서 로컬로 앱을 띄우는 방식(Docker와 로컬 Supabase)은 설치와 발열 부담이 커서 선택하지 않는다.
4. **예비 영상의 길이와 음성.** 추천은 장면별 1~2분, 설명은 발표자가 직접 말하는 것이다(음성 없는 영상).
5. **분석 예비안을 쓴 경우의 표현.** 추천은 화면에 "기존 벨루 결과"라고 표시하는 것이다. 새 앱의 결과처럼 보이게 하지 않는다.
